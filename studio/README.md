# SIA.HAUS 스튜디오 사이트 — `www.sia.haus`

아임웹에서 옮겨오는 소개 사이트입니다. 구조는 `license/` 와 같습니다.

```
data/site.json  ──build.py──▶  index.html   (본문 · JSON-LD 전부 인라인)
                               llms.txt
                               sitemap.xml
```

```bash
python build.py            # 생성
python build.py --check    # 파일을 쓰지 않고 검증만
```

---

## 왜 아임웹에서 옮기는가

아임웹에서 **할 수 없던 것**이 여기서는 전부 기본값입니다.

| 아임웹에서 | 여기서 |
|---|---|
| `VideoObject` 오류를 못 고침 (아임웹이 자동 삽입) | 마크업 전체가 우리 것 |
| `robots.txt` 편집 불가 | 파일로 관리 |
| `llms.txt` 업로드 지원 불확실 | 빌드 산출물 |
| 보안 헤더 설정 불가 | `vercel.json` |
| FAQPage 를 넣어도 본문에 문답이 없으면 위반 | 문답이 본문에 실제로 렌더링됨 |
| 관리자 로그인이 있어야 무엇이든 가능 | `main` push 가 곧 배포 |

특히 마지막 줄이 이 이사의 실질적인 이유입니다.

## 설계 원칙

**빌드 시점에 정적 HTML 로 펼칩니다.** JSON 을 클라이언트에서 fetch 해 렌더링하면
봇이 받는 원본 HTML 이 껍데기만 남습니다. 이 사이트의 목적이 생성형 엔진에 인용되는
것이므로 그 방식은 쓸 수 없습니다. `build.py` 는 출력물에 **JSON-LD 외의 `<script>` 가
섞이면 빌드를 실패시킵니다.**

**읽는 사람에게 보이는 문자열은 전부 `data/` 에 있습니다.** `build.py` 에는 문구가
없습니다. 문구를 고칠 때 파이썬을 열 일이 없어야 합니다.

**JSON-LD 는 화면에 있는 내용만 옮겨 적습니다.** 화면에 없는 내용을 스키마로만
선언하면 구조화 데이터 위반이 되고, 생성형 엔진도 근거 없는 주장으로 취급해 인용하지
않습니다. `FAQPage` 를 실을 수 있는 것은 같은 문답이 본문에도 렌더링되기 때문입니다.

## 엔티티 연결

`Organization` 의 `@id` 는 **세 곳에서 글자까지 같아야** 하나의 엔티티로 합쳐집니다.

```
www.sia.haus/#organization  ──subOrganization──▶  varis.kr/#organization
                            ◀──parentOrganization──
```

| 파일 | 역할 |
|---|---|
| `studio/data/site.json` → `site.org_id` | 이 사이트가 선언하는 자기 `@id` |
| `academy-varis/build_jsonld.py` → `PARENT_ORG_ID` | varis.kr 이 부모로 가리키는 값 |

두 곳뿐입니다. 아임웹 시절 스니펫(`infra/geo/imweb-head-snippet.html`)에도 같은
`@id` 가 있었지만, 붙여넣을 곳이 없어져 2026-09-16 에 삭제했습니다.

**대표 도메인을 non-www 로 바꾸면 위를 함께 고칠 것.** 한쪽만 고치면 관계가 조용히
끊기고, 끊겨도 아무 오류가 나지 않아 눈치채기 어렵습니다.

## 확정이 필요한 값

`data/site.json` 의 `licensing.launched` 는 **`false`** 입니다 — 구독 라이선싱이
아직 출시 전임을 2026-09-16 에 확인했습니다.

그래서 정의문이 "작가 IP로 축적하고 있습니다" 로 끝나고 라이선싱 FAQ 가 빠집니다.
**출시하면 `true` 로 바꾸면** 정의문 뒷부분과 FAQ 가 함께 복구됩니다. 없는 서비스를
정의문에 넣으면 첫 문의부터 어긋나기 때문에, 모를 때 더 크게 주장하지 않습니다.

`license/` 사이트(구독 라이선싱 카탈로그)도 **출시 전에는 배포하지 마세요.**

그 밖에 값이 생기면 채울 곳:

| 항목 | 넣을 자리 |
|---|---|
| 대표 전화번호 | `site.telephone` 추가 후 `build_jsonld` 에 연결 |
| 사업자등록번호 | 공개 시 신뢰도 신호로 유효 |
| 인스타·유튜브·링크드인 | `site.same_as` 배열 |

## 실적 연도

`work.items` 의 `year` 는 **확인된 것만** 채워져 있습니다. 출처는
`infra/geo/llms.txt` 와 `project/readme.md` 이며, 그 두 곳에 연도가 없는 항목은
비워 뒀습니다. 화면에서는 연도 칸이 그냥 비고, `llms.txt` 에서도 빠집니다.
아는 연도가 있으면 채우시면 됩니다 — **추정해서 넣지 마세요.**

## 실적 행 구조

Esme(Webflow 템플릿, https://webflow.com/templates/html/esme-website-template)의
프로젝트 행 구조를 가져왔습니다. 가져온 것은 셋입니다.

1. **중간 크기를 두지 않습니다.** 클라이언트명이 디스플레이 크기, 나머지는 전부
   14~16px, 그 사이가 없습니다. 한 줄이 한 작업으로 읽히게 하는 건 이 대비입니다.
2. **연도를 같은 베이스라인의 오른쪽 끝에** 붙입니다. 가운데로 모으지 않고 양 끝으로
   밀어, 그 사이 여백이 구분선 역할을 합니다.
3. **행 전체가 링크**입니다 (`url` 이 있을 때).

`work-client` 는 **h2(최대 40px)보다 작게** 유지합니다. 처음에 44px 로 뒀더니
1280px 에서 행 하나가 섹션 제목보다 커져 위계가 뒤집혔습니다.

### 가져오지 않은 것

원본은 **전면 사진 위에 텍스트를 얹고** 스크롤에 따라 패널이 겹쳐 올라옵니다. 둘 다
빼두었습니다.

- 이 저장소에 **작업 이미지가 없습니다.** 사진 없이 전면 패널을 쓰면 13개 화면이
  빈 색면으로 이어집니다.
- 스크롤 연동 리빌은 JS 가 필요합니다. 이 사이트는 **JSON-LD 외의 `<script>` 가
  들어가면 빌드가 실패**합니다. `position:sticky` 로 겹침 자체는 JS 없이 되지만,
  그것도 이미지가 생긴 뒤의 일입니다.

원본은 행마다 `View Project` 라는 **같은 문구**를 씁니다. 스크린리더에는 이름이
똑같은 링크가 13개 생깁니다. 여기서는 행을 통째로 `<a>` 로 감싸 클라이언트명과
작업명이 링크의 접근성 이름에 들어가게 했습니다.

### `url` — 아직 비어 있습니다

`work.items` 의 `url` 은 **선택**입니다. 없으면 행은 링크가 아닌 그냥 행으로
렌더됩니다 — 갈 곳 없는 링크를 만들지 않습니다.

지금은 13개 전부 비어 있습니다. 이 값은 **「미결 — 프로젝트 상세 페이지」가 정해져야**
채울 수 있습니다. 상세 페이지를 만들면 `/seoullight` 같은 옛 주소를 `/#work`
프래그먼트가 아니라 **1:1 로** 보낼 수 있고, 그러면 지금 12개 규칙이 색인상 홈으로
가는 문제가 사라집니다. Behance 로 보내기로 하면 그 주소를 여기 넣으면 됩니다.

## 배포

Vercel 정적 배포. Root Directory 는 `studio` 입니다.

### HSTS

`Strict-Transport-Security` 는 **`max-age=63072000`(2년)** 입니다. varis.kr 과 같은
값입니다. 초기에는 전환 사고를 대비해 `max-age=300` 으로 두었다가 2026-09-20 에
올렸습니다.

**`includeSubDomains` 와 `preload` 는 일부러 빼두었습니다.**

- `includeSubDomains` 를 켜면 `license.sia.haus` 를 포함한 **모든 서브도메인**이
  2년간 HTTPS 로 고정됩니다. 아직 배포되지 않은 서브도메인이 있어, 그중 하나라도
  HTTPS 로 서빙하지 않으면 접속 자체가 막힙니다.
- `preload` 는 **되돌리기가 사실상 불가능합니다.** 브라우저 preload 목록에서
  빼는 데 수개월이 걸립니다.

varis.kr 도 같은 이유로 둘 다 없이 `max-age` 만 씁니다. 서브도메인이 전부 배포되고
HTTPS 가 확인된 뒤에 검토할 일입니다.

이 헤더는 **도메인이 Vercel 에 붙은 뒤부터** 방문자에게 적용됩니다. Vercel 은
인증서를 발급한 뒤에야 도메인을 서빙하므로, 방문자가 처음 닿는 시점에는 이미
HTTPS 가 동작합니다.

### 전환 순서

1. ~~Vercel 프로젝트를 이 저장소에 연결 (Root Directory `studio`)~~ ✅ 완료
2. ~~프리뷰 URL 로 내용 확인~~ ✅ 완료 — https://siahaus-design-system.vercel.app
3. 옛 URL → 새 주소 301 `redirects` 작성 ← **진행 중, 아래 참고**
4. DNS 를 Vercel 로 전환
5. ~~https 확인 후 HSTS `max-age` 상향~~ ✅ 완료 (2026-09-20, `max-age=63072000`)

3번을 건너뛰면 **기존 검색 순위를 그대로 날립니다.** 옛 주소를 알아야 리다이렉트를 깝니다.

### DNS — 전환 시 알아둘 것

`sia.haus` 의 네임서버는 **이미 Cloudflare** 입니다 (`liz.ns.cloudflare.com` ·
`curt.ns.cloudflare.com`). 아임웹은 호스팅만 하고 있으므로 **DNS 전환에 아임웹의
허락이 필요하지 않습니다.** Cloudflare 에서 레코드만 바꾸면 됩니다.

도메인 등록기관은 아임웹으로 보이며 Cloudflare Registrar 로 이전 예정입니다.
등록기관 이전은 DNS 를 건드리지 않아 사이트 동작과 무관하지만, **이전이 끝나기 전에
아임웹을 해지하면 도메인이 위험합니다.**

전환 후에는 아임웹 쪽 리다이렉트 문제(`sia.haus` → 302 → `http://www.sia.haus`)가
저절로 사라집니다. Vercel 이 apex→www 를 HTTPS 로 308 처리합니다.

## 리다이렉트 맵

`vercel.json` 의 `redirects` 에 있습니다. `statusCode: 301` 을 명시합니다 —
`permanent: true` 는 308 을 내보내는데, 301 이 검색엔진 문서에서 다루는 기준값입니다.

`vercel.json` 에 규칙이 **18개** 있습니다. 목록은 그 파일이 정본입니다.

| 도착지 | 규칙 수 | 해당 경로 |
|---|---|---|
| `/#work` | 10 | `/PROJECTS` `/SLW2025` `/seoullight` `/busan` `/heachi` `/reawakening` `/waterdrops` `/fluxcollision` `/luvita` `/universe-cube` |
| `/` | 7 | `/about` `/38` `/Material` `/LGISE` `/Artist` `/36` `/37` |
| `/#contact` | 1 | `/contact` |

경로 목록의 출처는 2026-09-20 에 다른 작업 환경(Aside 브라우저 — 이 저장소의
Claude Code 세션과 달리 `sia.haus` egress 차단이 없음)에서 라이브 `sitemap.xml` ·
`robots.txt` · 각 경로를 직접 읽은 커밋(`10bc8eb`)입니다. 아래 「2026-09-20 색인
조사」는 그 이전에 검색 색인만으로 간접 조사한 기록이라 **일부 결론이 틀렸고**,
직접 접근 결과로 대체합니다 — 상세는 다음 절 참고.

### `/#work` 로 보내는 10개 규칙에 대한 판단

이 표 바로 아래 「미결 — 프로젝트 상세 페이지」절은 "무관한 페이지로 리다이렉트
하는 것(예: `/#work`)은 soft-404 로 취급돼 하지 않는 편이 낫다"고 적어 뒀습니다.
일반론으로는 맞습니다 — 개별 페이지를 전부 **무관한 홈으로** 몰아 보내는 건
구글이 soft-404 로 취급하는 대표 패턴입니다.

다만 여기 10개는 그 패턴이 아닙니다. **홈이 아니라 같은 주제의 카테고리 페이지
(`/#work`, 새 사이트의 포트폴리오 섹션)로 보냅니다.** 단종된 개별 상품 페이지를
상품 목록 페이지로 리다이렉트하는 것과 같은 구조이고, 이건 구글이 명시적으로
허용하는 패턴입니다(무관한 페이지로 보내는 것과 다름). `/38`(IP 라이선싱)과
5개의 내용 없는 페이지만 실제로 "무관한 홈"으로 보내는데, 이쪽은 대응할 주제별
페이지가 아직 없어서(`license.sia.haus` 미출시) 남은 선택지가 홈 폴백뿐입니다.

**다만 위 논리에는 구멍이 하나 있습니다 — `/#work` 는 별도 URL 이 아닙니다.**
`#work` 는 프래그먼트라서 서버로 전송되지 않고, 검색엔진도 무시합니다. 즉 크롤러가
보는 리다이렉트 대상은 `/#work` 가 아니라 **`/`, 곧 홈입니다.** "홈이 아니라 카테고리
페이지" 라는 구분이 프로토콜 수준에서는 성립하지 않습니다. 10개 전부 색인 관점에서는
홈으로 가는 리다이렉트이고, 바로 위에서 안 된다고 적은 그 패턴입니다.

사람에게는 여전히 유용합니다 — 브라우저는 프래그먼트를 처리하므로 방문자는 실적
섹션에 도착합니다. **사람에게는 이득, 검색엔진에는 무의미** 정도가 정확한 평가입니다.

카테고리 리다이렉트 논리를 진짜로 쓰려면 `/work` 를 **독립된 URL** 로 만들어야
합니다. 지금 사이트는 단일 페이지라 그런 URL 이 없습니다.

**그래도 완전한 해법은 아닙니다.** `/#work` 는 최근 실적 목록일 뿐 옛 10개
프로젝트 각각의 개별 콘텐츠(제작 규모, 클라이언트 코멘트 등)를 담고 있지 않아서,
검색엔진이 그 페이지를 "같은 내용의 새 위치"로 인정하지 않을 수 있습니다. 진짜
등가 대체는 아래 「미결 — 프로젝트 상세 페이지」의 두 번째·세 번째 선택지(상세
페이지 재제작, 또는 Behance 로 개별 리다이렉트)뿐입니다. 지금 규칙은 **아무것도
안 하는 것보다는 낫지만, 확정판이 아니라 잠정 조치**로 남겨 둡니다.

### 2026-09-20 색인 조사 (간접 조사, 직접 접근으로 대체됨)

> 아래는 `sia.haus` 접속이 막혀 있던 작업 환경에서 검색 색인만으로 조사한 기록입니다.
> **핵심 결론 두 가지가 직접 접근 결과와 다릅니다** — `/about` 은 색인에 없었을 뿐
> 실제로는 라이브 페이지였고(아래 참고), `/contact` 는 아임웹 자체가 이미 `/` 로
> 301 리다이렉트하고 있어 소개문 운운은 오래된 캐시로 보입니다. 조사 과정 기록으로만
> 남겨 둡니다.

검색 인덱스에 잡히는 `sia.haus` 주소는 **세 개뿐입니다.**

```
http://sia.haus/                제목: sia.haus
http://sia.haus/contact         제목: about - namecode
http://sia.haus/universe-cube   제목: UNIVERSE cube - SIA
```

세 가지 질의(`site:`, 한국어 키워드, 영어 섹션명)에서 모두 같은 세 개만 나왔고
`/about` 은 한 번도 나오지 않았습니다.
